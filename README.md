# ConsultBae AI Automation Assignment

Merges three messy people-datasets into one SQLite DB, tags people's skills with an
n8n + LLM automation, and runs a mini browser audio-collection app on top of the
same DB.

## 🚀 Live Demo

**App is live at:** https://consultbae.onrender.com/

## Setup

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
```

Audio transcoding uses `ffmpeg` under the hood (via `pydub`) — install it if you
don't have it: `sudo apt install ffmpeg` (Linux) / `brew install ffmpeg` (Mac).

### 1. Run the merge pipeline (Task 1)

```bash
python3 db/merge_pipeline.py
```

Produces `consultbae.db` (a `people` table with one row per real person, a
`source_records` table with the full audit trail of every raw row that fed into
each person, and an empty `audio_submissions` table for Task 3) and
`data_issues_log.json`. Re-run any time — it's idempotent, rebuilds the DB from
scratch from the CSVs in `data/`.

See `DATA_ISSUES_REPORT.md` for exactly what was wrong with the data and how each
issue was resolved — including one case (two different people both named "Arjun
Mehta") the pipeline deliberately refuses to auto-merge because it can't be
resolved safely from the data alone.

### 2. Run the audio app (Task 3)

```bash
cd app && python3 app.py
```

Open `http://localhost:5000`. Enter a name + phone, record from the mic (or
upload a file), submit. It extracts **duration, sample rate, bitrate, loudness
(dBFS)**, and a rough quality estimate, stores the file + a DB row, and — if the
phone number matches someone from Task 1 — links the submission to that person.
`http://localhost:5000/submissions` lists everything with a play button.

To deploy publicly for the video (so it's not just `localhost`): easiest is
`ngrok http 5000` while `app.py` is running — no other changes needed, use the
`https://xxxx.ngrok-free.app` URL it gives you in your recording.

For a longer-lived public URL (e.g. Render free tier):
- `app.py` reads `PORT` from the environment and defaults `FLASK_DEBUG` off in
  prod, so no code changes needed there.
- The build image needs `ffmpeg` — Render's default Python image doesn't have
  it, so either use a Docker-based service with an `apt-get install -y ffmpeg`
  step, or add a `render-build.sh` that runs it before `pip install`.
- `consultbae.db` is gitignored on purpose (it's a build artifact, not source).
  Add `python3 db/merge_pipeline.py` as part of the build/start command so the
  DB exists before `app.py` runs — e.g. start command:
  `python3 db/merge_pipeline.py && python3 app/app.py`.

### 3. Run the n8n automation (Task 2)

This one **needs to actually be executed inside n8n** — it's not something a
script can demonstrate on its own, since the whole point is showing the no-code
tool running.

1. Sign up for n8n Cloud (free trial) or run self-hosted (`npx n8n`).
2. Workflows → Import from File → `n8n/skill_tagger_workflow.json`.
3. Add your own LLM credential to the "LLM: classify skill category" node
   (OpenAI, or swap the node for Anthropic/whatever you have access to — the
   prompt is provider-agnostic).
4. Make sure `app.py` is running and reachable at the URL the two HTTP Request
   nodes point to (`localhost:5000` if running n8n locally against your own
   machine; if using n8n Cloud, expose `app.py` via `ngrok` first and update the
   URLs).
5. Click **Execute workflow**. It pulls everyone in `people` who has skills but
   no `skill_category` yet, asks the LLM to bucket each person into
   `automation-heavy` / `web dev` / `data` / `ai/ml`, and writes the tag back via
   `POST /api/people/<id>/tag`.

I built and tested the two Flask API endpoints it depends on
(`GET /api/people/untagged`, `POST /api/people/<id>/tag`) directly with `curl` —
both work. What I could **not** do inside this environment is actually run n8n
itself or call a real LLM (no n8n instance, no API key here) — so you'll be the
one clicking "Execute" for the first time. Budget time for this; it's usually
where small things go sideways (auth setup, the exact JSON shape n8n expects from
an HTTP node, etc).

## Stuck log

*(Fill this in with your own words before submitting — this is exactly what gets
checked on the live call. Below are the real technical snags this build hit,
as a starting point, not a finished answer. Rerun things yourself, hit your own
version of these, and write what you actually did.)*

**1. Browsers don't record WAV.**
`MediaRecorder` in the browser produces `webm`/Opus, not the plain WAV that
`soundfile`/`librosa` read natively. First pass at `audio_analysis.py` threw on
every real recording. Fix: transcode everything through `ffmpeg` (via `pydub`)
to a temp WAV before analysis, for both recorded *and* uploaded files, so the
pipeline is format-agnostic either way.

**2. The name+city fallback match silently merged two different people.**
Two different "Arjun Mehta" exist in the data (real trap in `source3`, they're
both in Noida but have different phone numbers). Naive "match by name+city if
there's exactly one candidate" logic **passed its own test** — because at the
moment the ambiguous gig-worker record (no phone) was being matched, only one
of the two Arjun Mehtas had a `people` record yet, so it looked unique. Caught
by spot-checking that specific person after the first pipeline run, not by an
error — the code ran fine and produced a wrong answer, which is worse. Fix:
compute ambiguity globally upfront (do more than one phone number attach to
this name+city anywhere in the raw data?) instead of checking against
partially-built state.

**3. CTC units.**
`Current CTC` mixes absolute rupees and lakhs with nothing distinguishing them
except magnitude (`417964` vs `4.2`). There's no fully safe way to tell these
apart from the data alone — the `< 1000 → lakhs` heuristic is a judgment call,
documented as such rather than presented as certain. A real version of this
would flag these rows for a human to confirm rather than silently convert.

## Task 5 — stretch: what breaks at 5,000 gig workers over a weekend

See below (kept short, no code, as the assignment asks).

- **Storage**: raw audio saved to local disk (`uploads/`) doesn't survive a
  redeploy on Render/Railway free tier and isn't shared across instances if
  the app scales beyond one process. First real fix: object storage (S3 /
  Cloudflare R2) instead of local disk, referenced by URL in the DB.
- **Uploads**: no chunking/resumability — a flaky mobile connection mid-upload
  on a multi-MB recording just fails outright with no retry. Would add
  client-side retry with backoff, and cap/compress client-side before upload.
- **Duplicates**: nothing currently stops the same person submitting the same
  clip 5 times if the button gets tapped twice on a bad connection, or
  resubmitting entirely new recordings under a slightly different name/phone.
  Would add idempotency keys client-side and a phone+time-window duplicate
  check server-side.
- **DB**: SQLite is fine for this assignment but does not handle concurrent
  writes from thousands of simultaneous submitters — first thing to swap for
  Postgres before any real traffic.
- **Analysis cost**: `ffmpeg` transcode + feature extraction runs synchronously
  in the request today, so a burst of concurrent submissions would queue up
  behind slow transcodes and start timing out requests. Would move analysis to
  a background job queue (the submission returns immediately, analysis catches
  up async) rather than blocking the HTTP response.
- **Cost**: 5,000 people × even a small clip each adds up in storage +
  bandwidth fast if clips aren't compressed/bitrate-capped on ingest; would
  also want basic rate-limiting per phone number to stop abuse.
- **Failures**: no dead-letter/retry path today if transcoding throws (e.g. a
  corrupt upload) — it's currently caught and the submission is saved with
  `quality_estimate: unknown`, which is a reasonable fallback, but there's no
  alerting on how often that's happening in aggregate.
